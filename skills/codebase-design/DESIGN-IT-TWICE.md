# Design It Twice

用户希望为选定候选项探索不同 Interface 时，用这套方案比较方法。它借鉴 Ousterhout 的 “Design It Twice”：先比较有实质差异的方案，再做选择，不把第一个想法当成唯一答案。

使用 [SKILL.md](SKILL.md) 中的术语：**module**、**interface**、**seam**、**adapter**、**leverage**。

## Process

### 1. Frame the problem space

比较前，先说明所选候选项的问题范围：

- 新 Interface 必须满足的约束
- 它依赖哪些对象，以及这些依赖属于哪一类（参见 [DEEPENING.md](DEEPENING.md)）
- 一段粗略的示意代码，用来具体呈现这些约束；它不是方案，只是帮助说明约束

在已有授权内继续比较，不因进入此流程重复请求批准。

### 2. Explore alternatives

选择值得比较的不同方向，通常两个方案已足够。环境支持且独立探索确有收益时可分派 sub-agent；否则在当前会话完成。数量由真实取舍决定，不为满足配额制造方案。

并行比较时，为每个 agent 提供足够的文件路径、耦合细节、依赖及约束，并给出不同探索方向。例如：

- 尽量降低调用方需要掌握的概念，保持入口含义明确。
- 保留已知的独立使用场景和变化方向，不为假想扩展增加接口。
- 优先照顾最常见的调用方，让默认场景简单。
- 若跨依赖的隔离是关键取舍，探索 ports & adapters 的收益与成本。

在说明中复用项目已有领域词汇，并在需要时映射到 [SKILL.md](SKILL.md) 的术语。没有 CONTEXT.md 或其他词汇表时直接使用代码和需求中的词汇，不为本流程新建文件。

每个方案说明：

1. Interface（类型、方法、参数，以及不变量、顺序约束和错误模式）
2. 展示调用方如何使用该 Interface 的示例
3. Implementation 在 Seam 背后封装的内容
4. 依赖策略和 Adapter（参见 [DEEPENING.md](DEEPENING.md)）
5. 取舍：Leverage 较高和较弱的方面

### 3. Present and compare

按任务规模展示关键接口或调用示例，再比较调用方认知成本、变化集中度、依赖隔离、兼容与迁移成本、实际可验证性。若调整测试结构，说明旧行为覆盖如何承接。

比较后给出自己的建议：说明你认为哪个设计最有优势，以及原因。如果不同设计中的部分内容适合组合，可以提出 hybrid 方案。要明确表达判断，用户需要的是有依据的结论，而不是一份选项清单。
