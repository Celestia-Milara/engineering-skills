# Clarify Work

主动采访用户，把模糊想法、未经检验的假设和“看起来合理”的方案，追问成双方理解一致的需求与设计理由。不能只复述用户想做的功能，或因为已经能开始写代码就结束访谈。

## 选择访谈深度

- **深入访谈**：项目初期、探索新方向、核心设计尚未形成，或用户说“grill / 拷打我 / 彻底梳理”。这是本技能在项目初期的主要用途。系统探索本次项目范围内的重要需求和设计分支，持续多轮追问。
- **局部澄清**：已有稳定需求，只需确定某个功能的行为或边界。围绕该问题收敛，不重新访谈整个项目。

根据用户意图选择，说明本次访谈范围。用户要求深入访谈时，不能自行降级为“解决下一步阻塞项”。范围可随回答修订；不确定会实质改变访谈范围时再询问。

## 从已有事实开始

有项目资料时读取相关代码、测试、项目说明和已有领域词汇表；按 [decision-notes](../decision-notes/SKILL.md) 检索相关约束。尚无代码的新项目直接从用户、问题和使用场景开始。环境中可查的事实自己查；用户的真实目标、偏好和业务经验通过提问获得。

明确区分现有行为、目标行为、用户已决定的约束、委托你判断的事项，以及尚未验证的假设。已有授权和决定不重复索要批准；仍可追问其理由、适用条件和代价，发现矛盾时指出具体冲突。

## 按设计树多轮追问

深入访谈时读取 [references/project-interview.md](references/project-interview.md)，使用其中的追问方向和反例方法。它是检查覆盖的参考，不是照顺序填写的问卷。

维护一棵需求与设计树：一个回答会产生新的问题、约束或取舍。每个重要分支标记为已明确、待回答、待验证或明确延后；只有实际需要跨会话时才把树保存成文件。

每轮执行：

1. 根据上一轮回答找出含糊词、隐含假设、冲突、尚未解释的选择，以及新产生的分支。
2. 选择前置条件已明确的问题组成当前轮。互不依赖的问题可以一起问；依赖某个未回答问题的留到后续轮，不能替用户猜前提。
3. 用编号问题说明要解决的取舍。合适时给出推荐答案、备选与代价；了解真实需求的开放问题先让用户描述，不用推荐答案诱导用户接受你的假设。每轮问题数量按认知负荷调整，不能用固定少量问题代替覆盖。
4. 等用户回答后重新计算问题树。回答“都要”“越快越好”“应该不会”时，追问优先级、阈值或反例；回答产生新矛盾时继续深挖，不自动判为已解决。
5. 简短回述本轮形成的理解及理由，方便用户纠正，再进入下一轮。

真正需要用户决定的事项保持待定；等待期间可继续独立调查，不能把沉默当作回答。用户明确委托的技术细节可以由你比较并提出结论，不强迫用户替你做工程调查。

## 用场景和理由检验回答

- 从实际使用过程提问，逐步检查正常、失败、边界与恢复场景。选择能挑战当前模型的反例，不限制为一个正常场景加一个异常场景。
- 对重要选择追问“解决了什么问题”“为什么采用它而非备选”“付出的代价”“什么变化会让它失效”。先看用户需要的行为，再检验方案是否必要；不要默认用户提出的技术方案就是需求本身。
- 当两个要求不能同时成立时，用具体场景揭示冲突，要求给出取舍或优先级，不把矛盾藏进实现细节。
- 术语有歧义时，用具体行为解释区别。需要跨会话反复使用的已确定术语才写入已有词汇表，没有时再创建 `CONTEXT.md`。
- 词汇表只描述业务含义和关系，不保存任务进度、实现设计或未定假设。不为普通 CRUD 强建领域模型。
- 已形成且值得长期保留的设计理由及时按 decision-notes 判断是否记录；真实备选及取舍不能只留在聊天里。不另建 ADR，尚未定案或未落地的方案按 decision-notes 选择状态，不能自动写成 accepted。

## 保存理解

用户要求保存、访谈明显跨会话或需要团队共同使用时，复用已有需求文档或工单；没有既有位置时写入 `.agents/work/<主题>/requirements.md`。维护目标用户、问题与场景、范围与优先级、验收、关键选择的决策链接、未解决问题和明确延后项。范围和需求级验收只保留一个维护来源；计划引用相应条目并补充实施切片，不另维护一份需求正文。用户随后调整需求时，按已有写入授权同步该来源，再调整受影响的计划；暂未同步的来源注明差异，不能继续当成最新要求。

3–4 人协作时，识别哪些业务问题当前回答者无权或无法确定，谁能补充事实、谁有明确的决策权。记录已知责任与分歧，不替未参与的同事表态，也不擅自联系他们。TS / Python 选型或跨端契约只在影响项目目标或边界时深入讨论。

## 结束条件

**深入访谈**在本次范围内的每个重要分支都满足以下之一时进入总结：已明确；由用户明确延后且说明影响；满足下述待验证条件。总结包括目标与成功标准、关键场景、范围及优先级、设计选择和真实理由、备选代价、待验证假设。不能以“足以写第一步代码”替代这个条件，也不能替用户把困难问题标为延后。

需要实验才能确定的性能、可行性或效果，可以保留为待验证：先明确相关需求、判断成立或失败的标准、下一项验证动作，以及它阻塞哪些选择或实施切片。满足这些条件可以结束访谈，不等于假设成立或阻塞解除。仍需用户回答的业务目标、优先级和取舍保持待回答，不能改标待验证来绕过。

**局部澄清**在该功能的行为、边界和有关取舍明确时即可结束。

把总结交给用户核对是否准确；已通过多轮回答明确的选择不重复请求批准。仍有未回答的关键问题就继续访谈或明确说明未完成，不能宣称已达成一致。用户要求暂停或只完成部分时，保存已明确内容和剩余分支。

需要实施切片时可使用 plan-work。只请求访谈时交付理解与问题，不自动开始实现；用户已授权后续实现且理解已明确时可继续。
