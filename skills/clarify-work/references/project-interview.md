# 项目初期的深入访谈

目的是主动挖出用户尚未表达清楚的需求和设计原因。根据回答展开问题树，持续追问到本次范围内的重要分支得到处理，不把访谈变成固定问卷。

## 需求与设计的检查方向

这些方向用于发现遗漏。与项目无关的略过，有重要分歧或假设的方向深入追问。

| 方向 | 第一层问题 | 继续追问什么 |
| --- | --- | --- |
| 用户与问题 | 谁在什么情境下遇到什么问题？现在如何处理？ | 频率、具体损失、现有替代办法；没有这个产品会怎样 |
| 目标与成功 | 做成后，什么可观察结果说明有用？ | “方便”“快”“准确”的具体含义；怎样发现方案没解决问题 |
| 使用过程 | 拿一个真实案例，从开始到结束走一遍 | 输入来自谁、关键状态、谁做决定、输出被如何使用 |
| 边界与恢复 | 失败、重复、取消、中断、离线或错误输入时怎样？ | 哪些必须自动恢复，哪些可人工处理；不可逆操作的后果 |
| 范围与优先级 | 第一版最少要让哪条完整路径成立？ | “都要”时谁优先；哪些删掉仍有价值，哪些删掉目标就不成立 |
| 领域概念 | 用户使用的词指哪些对象、动作和关系？ | 一个词是否混了两个概念；举反例测试对象边界 |
| 设计原因 | 为什么倾向这个方案？真正约束是什么？ | 可行备选、维持现状、代价和重新评估条件；偏好与硬约束分开 |
| 数据与外部边界 | 数据在哪里产生、谁拥有、谁依赖它？ | 一致性、隐私、错误、兼容、保留期限等实际相关约束 |
| 现实能力 | 时间、运行环境、维护能力和团队怎样限制选择？ | 3–4 人实际分工、知识缺口、谁能补充信息；不预设人名或职责 |
| 验收与验证 | 怎样判断行为满足需求？哪些假设需实验？ | 代表性输入输出、失败标准、证据来源；未验证不写成事实 |

技术栈并非第一轮默认话题。用户已确定 TS / Python 时接受它作为输入，追问的是该选择带来的实际边界和成本，而不是重复要求选语言。

## 追问方式

- **具体化**：“你说批量导入要快，一次大约多少条？多久完成会影响使用？”
- **反例**：“如果只导入了一半就断网，重试时你希望已有数据怎样处理？”
- **取舍**：“离线可用和多人实时一致发生冲突时，哪一种结果更不可接受？为什么？”
- **理由**：“为什么需要完全自动处理？如果先给用户确认，哪一步价值会消失？”
- **检验假设**：“你说用户不会重复点击，有现有行为证据，还是界面上尚未限制？”
- **重新评估**：“什么情况出现时，你会接受从本地文件迁移到数据库？”

语气可以直接、持续挑战推理，但不要挖苦用户。用户明确拒绝讨论或要求缩小范围时遵循其范围，并记录剩余问题。

## 问题树示例

用户：“我想做一个自动整理会议记录的工具，TS 前端、Python 后端。”

先了解实际问题和使用过程，而不是直接规划转写、摘要和数据库模块：

1. 谁整理，现有材料是什么，当前最费时间的是哪一步？
2. 整理结果用于个人回顾、团队行动项，还是正式纪要？成功标准怎样判断？

如果回答是“团队行动项”，新分支包括负责人识别、期限、确认流程、误分配的代价。先明确使用目的，才有条件讨论这些分支。若用户要求“直接分派”，继续追问谁可以代表团队确认、模型不确定时怎么办；不能把“自动分派”作为已经正确的需求直接写进计划。

回答确定了人工确认后，再检验无人确认、部分确认、重复处理和跨会议冲突等与第一版有关的场景。确认后的长期选择及其真实取舍由 decision-notes 管理，尚未验证的摘要质量留在需求文档的假设中。

## 覆盖检查

总结前回看：是否只列了功能却没理解问题？是否知道关键设计为何成立、备选为何不合适？是否把含糊答案当成确定答案？是否遗漏由上一轮回答产生的分支？明确延后是否出自用户，以及是否影响第一版目标？需要实验的假设是否已有相关需求、判据、验证动作和阻塞范围，符合入口中的结束条件？

本轮无法回答的关键业务问题保持待回答；它与已明确验证方式的实验假设不同。推荐意见是帮助用户理解取舍，不能充当用户已经回答的证据。
