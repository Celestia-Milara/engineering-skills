# Choosing Test Doubles

默认通过稳定的行为接口验证真实实现。替身（fake、stub、mock）用于解决具体的反馈问题，不按“自己编写／第三方”一刀切：

- 时间、随机性、并发调度等需要确定性控制。
- 超时、断连、部分失败等需要可重复的故障注入。
- 真实依赖昂贵、缓慢、难以准备，或会产生支付、发送消息等实际副作用。

优先使用项目已有的测试入口和替身。替换点可位于外部依赖，也可在模块内部；应有稳定契约和上述实际理由，不为测试暴露私有实现，也不把要验证的业务逻辑整个替换掉。

## Keep assertions about behavior

断言用户或调用方关心的结果。必要的外部交互、幂等性或操作顺序可以是业务契约，例如一次订单重试不能导致重复扣款；没有业务含义的内部调用次数和顺序不应成为规格。替身的返回、错误和状态变化应来自真实契约，而不是迎合当前实现。

## Verify the production implementation

替身通过只证明该替身条件下的行为，不证明真实集成可用。按本次改动和风险保留生产 Adapter 的契约或必要集成证据：

- 数据库／文件替身：检查目标行为依赖的事务、并发、扩展或路径语义；缺失部分使用真实依赖验证。
- HTTP／队列 Adapter：覆盖相关序列化、错误映射和协议行为，必要时运行提供方契约、沙箱或集成检查。
- 自有远端服务：内存 Adapter 可验证业务规则，但不能证明生产者与消费者兼容。

无需每次改动都访问真实外部服务；优先复用已有可信证据，按影响范围补充检查。无法验证的部分要明确记录，不把 mock 通过报告为集成通过。

## Design replacement points deliberately

需要替换的依赖可通过参数或项目现有注入机制传入：

```typescript
function processPayment(order, paymentClient) {
  return paymentClient.charge(order.total);
}
```

用明确的领域操作表达依赖契约通常比在测试中解析通用请求更清晰，例如 `getUser(id)`、`createOrder(data)`。已有通用客户端若契约明确且足以验证目标行为，无需仅为 mock 再包一层。不要为凑够两个 Adapter 或追求所有对象都能替换而增加抽象。
