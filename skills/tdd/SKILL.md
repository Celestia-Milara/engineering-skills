# TDD

沿用 Matt Pocock 的行为测试与纵向切片方法，测试入口选择遵循已有授权和项目惯例。

## 选择可观察的入口

先读取相关代码、测试和 [decision-notes](../decision-notes/SKILL.md) 的约束检索规则。有领域词汇表时复用其术语。

找到用户或调用方观察行为的公开接口：函数结果、API 响应、CLI 输出、可见 UI 等。优先现有测试入口，选择真实覆盖目标行为且反馈足够快的层级。

已有计划、项目惯例或用户委托足以确定入口时直接使用并说明。只有新增接口带来范围变化、重要成本或业务含义未定时才询问，不逐个测试请求确认。接口本身需要重新设计且 codebase-design 可用时，按需读取它。

## 循环

1. 根据需求或已知故障写一个行为测试；期望来自独立的验收事实或算例，不照抄实现算法。
2. 运行它，确认因目标行为尚未满足而失败。导入、环境、语法错误先修正，不能当作 red 的证据。
3. 写足以通过这个测试的实现，再运行相关检查。
4. 若本片确需局部整理，在保持检查通过的前提下进行；不要趁机做大范围重构。继续下一条行为。

不要先批量写完全部测试再批量实现。默认通过稳定的行为接口测试，不用私有方法或内部调用次数替代真实行为；禁止重复扣款、持久化格式、必要操作顺序等真实交互契约可以直接断言。使用项目已有测试框架，不为了 TDD 新增运行时。

需要示例时读 [tests.md](tests.md)，需要替身选择与真实性验证时读 [mocking.md](mocking.md)。为确定性、故障注入或昂贵依赖使用替身时，依赖是否自有不是唯一判断标准；按风险保留生产实现的契约和必要集成验证。替换旧测试前确认有效行为覆盖已承接。

两份参考根据上游改编；TypeScript 示例不限定目标项目语言，按真实接口和契约判断适用性。

无法运行时明确说明哪些测试只是写好、尚未验证，不宣称 red/green 已完成。结束时报告观察到的失败与通过结果，以及尚未覆盖的关键行为。
