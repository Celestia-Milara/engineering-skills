# Debug Work

先建立能识别用户所说故障的信号，再用证据收敛原因。阶段按问题复杂度缩减，不机械要求固定数量的假设。

## 复现与现状

读取相关代码、配置、日志和测试，按 [decision-notes](../decision-notes/SKILL.md) 检索约束。明确期望行为、实际症状及触发环境。

首次修改文件（包括添加临时探针）前，检查当前分支或工作目录、已有修改及本次写入范围。区分用户、同事和自己新增的修改；重叠时先确认意图，不覆盖或清理已有工作。只请求定位时保持调查范围，不进入修复。

选择最便宜且真实覆盖故障路径的反馈方式：失败测试、CLI 输入、HTTP 请求、浏览器步骤或最小重放。实际运行并确认失败就是用户报告的症状，依赖缺失或启动失败不是复现成功。

尽量缩小输入和依赖，但不要把造成问题的并发、多调用方或时序条件一起删掉。偶发问题记录复现频率、运行次数和环境；不能把一次未发生当成已修复。

无法复现时可以继续静态调查并提出有依据的假设，明确标为未验证。指出最少还需要的日志、输入或环境，不凭猜测宣称根因或修复完成。生产侧取证需具备相应授权，凭证和个人数据不写入诊断产物。

## 验证原因

复杂问题列出少量有竞争力的假设；每个写清“如果成立，哪个可观察结果会改变”。一次改变一个关键变量，优先能区分多个假设的探针。

使用定向调试、日志或 profiling，记录关键证据，不堆无关输出。性能问题先在可比较条件下建立基线，再测量改动效果。临时探针使用可识别标记，收尾检查移除。

## 修复与验证

存在合适入口时先将复现变为失败回归测试，确认会捕获实际 bug，再实现修复并跑到通过。已有复现比单元测试更真实时保留它作为验证入口，不能用过浅的测试代替真实故障路径。

重新运行原始场景和受影响检查；性能与偶发问题记录对比条件、样本及剩余不确定性。清理自己新增的临时调试内容，保留有用的回归测试，不删除用户原有材料。

维护受影响的已有决策；普通局部 bugfix 不新建笔记。最终区分根因证据、改动、实际验证以及尚不能确认的部分。用户仅要求定位时，交付调查结论，不擅自实施修复。
