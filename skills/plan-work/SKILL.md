# Plan Work

计划描述要交付的行为和验证方式，篇幅随复杂度增加。不要把计划写成另一套长期决策记录。

## 建立输入

读取用户给出的需求、已有计划及相关代码、测试。按 [decision-notes](../decision-notes/SKILL.md) 检索约束，使用项目现有术语。已经知道的事实不再访谈；只有影响范围或正确性的未知项才询问，其他假设明确列出。

若用户要你保存计划，复用当前任务已有文件；无既有位置时写入 `.agents/work/<主题>/plan.md`。用户只要求简短规划时可以在回复中给出。已有工单是输入和引用来源，不要求安装或配置工单平台。

范围和需求级验收只保留一个维护来源，优先使用已有需求文档或工单；只有聊天输入时可在回复或计划中保留一份简明要求，不另建需求文件。已有独立需求来源时，计划引用相应条目，只补充切片级验收和执行安排。用户调整需求时，按已有写入授权同步需求来源，再更新受影响的切片；暂未同步的来源注明差异，不能继续当成最新要求。

## 最小计划

根据任务保留有用的字段，不用填空式扩写：

- **目标与范围**：简述要解决的问题和本次边界，详细需求引用维护来源。
- **验收行为**：引用需求级验收，补充各切片可观察、可判断的正常路径及有意义的异常路径；不用凑长篇 user stories。
- **现有约束**：相关决策笔记的链接，兼容性或迁移边界；拟议选择标为待定，不能冒充现行事实。
- **实施切片**：每片交付什么、怎样验证、真正的前置依赖。
- **验证方式**：从现有工具配置确认命令和测试入口。未运行的写“计划运行”，不写“通过”。
- **开放问题**：只列会影响执行的问题，并说明阻塞哪一片。

可写已核实的文件路径以便定位；路径是导航信息，执行前仍要复核。技术理由引用决策笔记，避免在两个地方同时维护。

## 切片原则

优先每片完成一条可观察的行为路径，贯穿它实际需要的层。不存在 UI 的项目无需添加 UI 步骤。每片应能独立验证，通常能在一次工作会话内完成。

不要默认拆成“全部数据库 → 全部后端 → 全部前端”。前置整理仅在确实降低本次实现成本时安排，范围要小，保持行为不变。

## 3–4 人协作时

只有需要多人接手的切片才补充负责人、共享位置和交付状态。负责人来自用户或已有任务分配，不虚构同事或擅自指派；未知时写待分配。

每片写清验收、依赖和交接入口。可使用待开始、进行中、受阻、完成四种简单状态，也可沿用现有工具状态；“完成”必须指明是本地实现完成还是已集成通过。

并行工作只有在依赖真实解除或接口契约已明确时才能开始。对 TS / Python 跨端接口，先明确字段、空值、错误、版本兼容和验证方式；引用已有 schema 或接口文件，不在每片复制一份。改变共享接口、数据库或基础配置时，标出受影响任务与集成先后顺序。

让有依赖的切片引用同一份计划或已有 issue。不要同时维护本地清单和另一套工单状态；需要团队读取时选择仓库中纳入版本控制的位置或现有共享工具。规划本身不授权创建外部工单或通知同事。

大范围机械迁移可采用“增加兼容形式 → 分批迁移调用方 → 移除旧形式”。指出哪些阶段可以独立保持检查通过；不能独立通过的必须有明确集成和验证点，不能假装每片都可单独交付。依赖不能形成环。

## 交付

给出建议先做的切片、计划位置和仍阻塞的取舍。不要自动发布工单、提交代码或开始实施仅规划的任务。用户已委托规划并实现时，计划完成后直接执行已明确且未被阻塞的切片。
