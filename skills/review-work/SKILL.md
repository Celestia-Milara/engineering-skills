# Review Work

以具体问题和可验证证据为中心，分别检查“做对了用户要的事”和“实现是否可靠”。两项结论不能互相抵消。

## 固定评审范围

先确认用户请求的对象、工作区状态与比较起点，记录实际使用的范围。

- **当前未提交修改**：查看 `git diff`、`git diff --cached` 及 `git status --short`，读取范围内新增但未跟踪的文件。已有 HEAD 时可用 `git diff HEAD` 查看跟踪文件的合并结果；不能因此漏掉新文件。
- **分支或 PR**：验证基线和被评审的 head，使用对应 merge-base 到 head 的差异，明确说明是否包含未提交内容。PR 核对实际目标分支及 base/head SHA，确保差异、代码和测试来自该评审版本；不默认本地 HEAD 就是 PR head。
- **明确提交区间**：按请求比较端点或单次提交；不要把所有比较都改成三点语法。
- **尚无首个提交或无 Git**：按用户给出的文件或现有快照评审，说明不能确认变更来源的限制。

“评审这次改动”且存在明确工作区改动时可直接采用该范围。基线有实质歧义才询问。空 diff 先检查新增文件和范围；仍无变化就说明无可评审变更。

本地版本与 PR 不一致时，优先读取对应提交的内容或使用独立检出，不隐式切换、重置或清理有未提交修改的工作区。无法取得对应源码、依赖或运行环境时，说明实际读取的 base/head 或快照，以及哪些结论和检查受限；不能把另一版本的测试结果归给本 PR。

并行写入时，最终评审和验证需要一个稳定窗口：暂停影响该范围的写入，固定 SHA 或未提交快照，再读取差异和运行相关检查。评审包含未提交内容时，SHA 相同但工作区或暂存区不同，也不能视为同一验证对象。需要取得版本或集成且已安装时可使用 `git-work`；未安装时直接核对上述范围。

## 找到标准

需求来源可以是当前用户请求、验收标准、计划、issue 或 spec，不要求工单平台。没找到需求就说明需求符合度无法完整判断，仍继续工程检查，不编造规格。

读项目规范、相关调用方、测试，以及 [decision-notes](../decision-notes/SKILL.md) 命中的约束。代码风格工具已覆盖的格式问题不重复报告。

## 两个检查视角

**需求符合度**：遗漏、错误或部分实现的行为；未经要求增加的行为；验收与实际验证是否一致。引用对应需求和具体实现位置。

**工程质量**：正确性、状态与错误处理、兼容性、相关安全问题、回归覆盖和可维护性。对照真实输入和调用路径，不仅凭代码形状猜问题。命名、重复、过度抽象等只在造成具体成本时提出，明确区分缺陷与设计建议。

对发现比较变更前后的行为，确认问题由本次改动引入、扩大或实际触发。与本次变更无关的既有问题不列为本次缺陷；确有必要提醒时单独注明，不能冒充本次引入的阻塞项。需求标准存在多个版本时先核对其维护来源和用户最新要求。

小团队的 PR 还要检查依赖是否已集成、接口生产者与消费者是否兼容、迁移顺序是否能执行。TS 类型检查不能证明 Python 端运行时数据满足契约；跨端行为以实际 schema、序列化结果和契约测试证据判断。

多份成果组合交付时，检查实际源成果和目标集成版本，以及组合后的相关行为；各分支分别通过不等于组合后通过。来源 ref/SHA 和合并记录用于确认评审对象与来源，不能代替完成或验收证据。

默认可以由同一 agent 分别完成这两轮。用户要求独立并行评审且环境支持时才分派；没有多 agent 不影响完成评审。

## 输出与边界

列出可采取行动的发现，附严重程度、文件位置、触发条件或证据以及影响。按严重程度排列并注明属于哪个视角；没有发现时直接说明，不为凑数列风格偏好。

保留两个视角各自的结论，同时说明范围和未能验证的部分。检查未运行不能写成测试通过。只请求评审时不改文件；用户已要求修复时，可以处理授权范围内的发现并复验。
