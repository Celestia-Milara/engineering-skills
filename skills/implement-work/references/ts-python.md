# TypeScript / Python 验证入口

在需要判断“运行什么、在哪运行、跨端如何验证”时读取。它是选择依据，不是给所有仓库安装一套工具的清单。

## 从项目事实找到命令

| 项目 | 先查 | 选择检查的依据 |
| --- | --- | --- |
| TypeScript | `package.json` 的 scripts 与 packageManager、lockfile、tsconfig、测试配置、CI | 沿用 npm / pnpm / yarn / bun 的现有选择；对目标 package 跑相关行为测试、项目已有类型检查，构建和 lint 按变更及项目要求执行 |
| Python | `pyproject.toml`、lockfile、requirements、测试配置、CI 和现有环境 | 沿用 uv / Poetry / venv 等现有环境；先跑相关测试，已接入 ruff / mypy / pyright 等才使用，别把工具选择当成任务 |
| TS + Python | 工作区布局、API/schema 定义、客户端生成与集成测试配置 | 分别验证修改涉及的两端；契约变化检查生产者输出、消费者解析和已有兼容策略 |

命令应来自读到的真实配置。例如看到 test 脚本不代表一定支持相同的文件过滤参数，先确认测试运行器。项目已有快捷命令优先，不盲目调用最新版本工具。

## TS 常见验证边界

- 行为逻辑：现有公开函数或模块接口的测试。
- API / CLI：实际请求或命令输入到输出，检查错误路径和边界值。
- UI：变更影响到交互才选择组件测试或浏览器验证；类型检查和成功构建不代表交互正常。
- 持久化或外部服务：沿用隔离的测试数据库、fixture 和测试配置，不把真实服务副作用当成默认测试手段。

## Python 常见验证边界

- 纯计算：代表性的已知结果与边界输入，期望值独立于被测算法。
- API / CLI：实际响应、退出码、输出格式及失败路径。
- 文件与数据任务：用小型 fixture 和临时目录验证内容、编码、空输入及所需幂等性，不依赖开发机现有数据。
- 异步或并发：保留真实触发条件，避免用串行 mock 让原故障消失。

## TS / Python 契约

当变更涉及跨语言边界，检查相关事项即可，不为每个任务全量展开：

- 缺失字段、`null`、可选字段和 Python `None` 的约定。
- 时间与时区、数字精度、枚举值、错误响应和版本兼容。
- 新旧客户端或服务端是否会同时存在，迁移期间谁先更新。
- 已有 schema / OpenAPI / 序列化模型的单一维护来源；有生成客户端时按项目命令重新生成并验证。
- 用真实契约的代表性输入输出或集成测试覆盖边界。不要只通过两边各自的类型检查就宣称跨端兼容。

这些事项的长期“为什么”按 decision-notes 判断是否记录；本次验收和执行顺序放在计划或 PR 中。
