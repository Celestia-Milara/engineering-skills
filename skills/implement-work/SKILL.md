# Implement Work

围绕用户已授权的结果工作，小步实现并及时获得反馈。输入可以是聊天中的明确要求，不强制要求 spec、工单或计划文件。

## 开始

读项目协作说明、相关代码和测试，确认当前分支、已有修改以及本次工作范围。区分用户已有修改和自己新增修改，不能为了得到干净目录清掉已有工作。

读取 [decision-notes](../decision-notes/SKILL.md) 并完成相关约束检索。先确定可观察的验收行为与实际可用的验证方式；命令来自项目配置，不假设 npm、pytest 或特定框架。

涉及重要取舍但未明确时只澄清该取舍，其他已确定工作继续。大任务有计划则复用计划，无计划且确需切片时使用已安装的 plan-work，或直接列一个简短切片安排。

TS / Python 项目需要确定检查入口、跨语言契约或测试隔离方式时，读 [references/ts-python.md](references/ts-python.md)。只使用项目已接入且与变更相关的工具。

多人协作先核对本次负责的切片、基线、前置依赖及重叠修改。不要覆盖同事工作或把未集成的依赖当成已完成；共享接口需要变化时标明影响与兼容顺序。负责人未知且影响写入范围时先澄清，其余只读调查可继续。

## 实现循环

一次完成一条有用的行为路径，运行最相关的检查，再推进下一条。

- 功能逻辑和缺陷修复适合自动回归时，使用已安装的 tdd；未安装时也应先构造能捕获目标行为的失败信号，再做最小实现。
- 文案、样式、配置等改动按实际风险选择构建、预览或人工检查，不为每次改字新增测试。
- 原因不明的故障先用已安装的 debug-work，或直接建立复现并验证原因，不连续猜测性改代码。
- 模块接口确需重新设计时可读取 codebase-design，不把普通功能扩成架构改造。
- 不同语言使用各自已有的反馈工具；不要为遵守流程引入新运行时。

失败时先判断是否由本次改动引起，说明已有故障与环境问题。不能运行检查时，继续完成能验证的部分，并保留未验证结论。

## 收尾

检查需求是否真正交付、是否引入范围外行为及回归风险。复杂变更可使用 review-work；未安装时直接分别检查需求与工程质量。修复本次范围内的明确问题，避免无关清理。

执行相关测试和项目要求的检查；按变更影响决定是否需要全量测试。检查通过后，除非又改了相关代码或出现新证据，不重复跑同一套验证。

按 decision-notes 更新受影响的事实、状态和引用，只在有必要时新增笔记。笔记与对应实现保持在同一组待交付变更中；执行提交时两者一起提交，该要求本身不触发 git commit。

已有计划才更新它的完成状态，不为记录进度新建决策笔记。若用户在实施中调整范围或验收，按已有写入授权同步需求维护来源，再更新受影响的计划条目；暂未同步的来源注明差异，只有聊天要求时无需为此新建文档。最终说明实现结果、实际验证和未解决限制，涉及笔记时附一行说明。提交、推送、发布和部署遵循用户已有授权，不因流程走到最后而默认执行。

团队交付还要说明基线或分支、共享接口及迁移影响、依赖是否已经集成。局部测试通过只代表该验证范围，不等于整个团队分支已验证；在实际集成版本上完成相应检查后再报告集成通过。
