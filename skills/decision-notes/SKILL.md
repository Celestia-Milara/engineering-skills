# Decision Notes

决策笔记保存**代码和测试无法可靠推导出的「为什么」**：设计意图、不能破坏的边界、被否决的方案。每个新会话都没有记忆，只能看到眼前的代码：一段写得别扭的代码，往往是为了避免死锁或兼容某个约束而故意为之，不知情的 Agent 会把它「优化」掉；三个月前被否决的方案，也会被一次次重新提出。笔记就是留给下一个会话的护栏。

它不是工作日志：不记录今天做了什么、思考过程、TODO 或进度，这些属于 PR 描述。

笔记放在扁平目录 `.agents/decisions/`。目录不存在表示暂无笔记，首次需要记录时创建。自动校验是可选的项目工具，不要求特定语言或包管理器，何时调用见第 7 节；校验只管结构与引用，内容由你负责。

## 1. Search Before Modifying Existing Code

无论任务大小都做，因为最容易误改的恰恰是「看起来只是小重构」的任务。目录不存在即可结束检索，否则：

1. 先读 `Applies-To: project-wide` 的笔记。
2. 把各笔记 `Applies-To` 里的仓库相对路径或 glob 与这次要改的文件逐一匹配。`rg` / `grep -ril` 能帮你找字段和字面路径，但不能替你解释 glob——不要把一次文本搜索宣称为完成了 glob 匹配。
3. 要改的文件里有 `Decision: <文件名>.md` 注释的，读它指向的笔记；再按路径片段和领域关键词补充搜索。
4. 命中后先读 `Status`、`Applies-To`、`Decision` 三处，确认相关再读全文。

同一任务内可复用已核实的匹配结果；改动范围扩大、笔记或相关文件变化时重新检查受影响部分，不因切换 skill 重复读取未变化的全文。已有路径匹配工具时优先用其结果并核对语义；没有时仍按上述步骤检查，不为一次任务新建索引。

查到之后：

- **accepted**：当作当前约束遵守。这次改动若会违反它，先判断用户是否已授权这项技术选择或迁移：已授权就继续实施，新方案在实际生效范围内转为 accepted 后才取代旧笔记；只有冲突超出授权范围，或仍有必须由用户决定的取舍时，才停下来说明并询问。不要悄悄绕过或改掉原结论。
- **rejected**：不要重新提出。只有前提确实变了才可以重提，并在新笔记里写明哪些前提变了。
- **superseded**：只当历史看，顺着 `Superseded-By` 找到现行的那篇。
- **proposed**：尚未定案或尚未生效，不要当作当前实现约束。它可以是已授权、正在实施的目标；是否可继续工作依据已有授权，不依据这个状态词重新请求批准。

## 2. When a Note Is Needed

判断标准：未来的 Agent 看到这段代码或这个契约，会不会想去简化它、绕开它，或重新提出一个已否决的方案？会就写；只看代码和测试就能理解原因，就不写。

通常需要写的改动：架构边界（模块依赖、进程通信、分层）、跨模块契约（API、事件、协议、schema）、持久化契约（数据库 schema、配置与文件格式、wire protocol）、重要技术选型（SQLite 还是 JSON、IPC 还是 HTTP）、非显然约束（为什么这里不能并发、为什么故意不用缓存）。

通常直接改代码、不新建笔记：格式化、拼写、简单重命名、普通 CRUD、局部 bugfix、补测试、依赖 patch 升级、纯机械重构。若这些改动改变了已有笔记中的名称、路径或行为事实，仍按第 3 节更新原笔记。

拿不准时倾向不写。笔记太多没人读，比少写一篇代价更大。

## 3. Update or Create

结合第 1 节的检索结果，只有三种情况：

- **已有笔记描述的就是这个决策**：就地更新，不新建；非核心的命名、路径或实现细节变了，直接改原笔记里的事实。
- **相关，但这是一个新的独立决策**：新建，并在正文里用相对链接引用旧笔记。
- **没有相关笔记**：新建。

判断「同一个决策还是新决策」的依据：`Decision` 一节的**核心结论**变了没有。结论变了（如 IPC 换成 Message Bus）就新建，生效后取代旧的；没变只是细节变了就原地更新。

取代旧决策时，旧笔记保留原文不删，只做两处修改：`Status: superseded`，加一行 `Superseded-By: ./新文件名.md`——「曾经为什么那样设计」仍有价值。只是部分取代时不要标 superseded：改窄旧笔记的 `Applies-To` 和 `Decision` 范围，并让新旧笔记互链。

分阶段迁移时，尚未生效的新方案保持 proposed，旧约束继续描述实际现状。已有部分生效时，仅把该部分写成 accepted 并明确适用范围，未实施目标留在计划或独立 proposed 笔记中；不能让相互冲突的 accepted 结论覆盖同一范围。决策生效指其声明的范围已实际遵循该选择：代码行为以当前代码为准，纯政策约束可在正式采用时生效；涉及部署状态的声明需有部署证据，本地实现不等于生产已迁移。

`rejected` 和 `superseded` 是两条不同的轨道：`superseded` 表示方案**曾经生效**、现已被取代，取代链的终点必须落在 accepted 笔记上（D103）；`rejected` 表示讨论过但**从未生效**，不能出现在取代链里——候选方案被否决时，旧笔记保持 accepted 不动，把被否决的那篇写成 rejected。已落地方案的回退也是 superseded 而不是 rejected：新建 accepted 笔记说明回退后的现行方案，并作为被回退那篇的 `Superseded-By`。

笔记原则上不删除，决策失效用取代或改窄 `Applies-To` 表达。只有决策对象整体消失（功能下线、模块删除）且保留只会误导检索时才删；删除前确认没有代码里的 `Decision:` 指针和 `Superseded-By` 指向它（否则 D110 / D101 报错）。原文仍在 git 历史里。

## 4. Note Format

文件名 `YYYY-MM-DD-<status>-short-topic.md`。日期是首次创建日，查实际日期，不要凭印象；状态词取 `proposed` / `accepted` / `rejected` / `superseded` 之一，必须与头部 `Status` 完全一致（D022）——目录列表因此能直接读出每篇笔记的生命周期，两者不一致时以修正文件名为准；主题用小写英文 kebab-case，描述决策主题而不是任务本身。

**状态变化就是一次重命名**：改完文件名，必须修掉所有指向旧文件名的地方——`Superseded-By`、正文相对链接、代码里的 `Decision:` 反向指针；漏改由 D090 / D101 / D110 报出。

```markdown
# Decision: <标题>

Status: accepted
Applies-To: src/worker/**, src/ipc/protocol.ts

## Context

为什么需要做这个决定：问题、约束、触发条件。

## Decision

现行方案是什么，边界在哪。

## Alternatives

- **方案 A** — 为什么看起来合理（对手最强的论据）；为什么最终没有采用。
- **不做 / 复用现有方案** — 为什么不够。

## Consequences

- Positive: 具体收益。
- Negative: 具体代价、上限，以及什么情况下应该重新评估。
```

头部字段：

- `Status`：必填，取值同上。
- `Applies-To`：除 superseded 外必填。逗号分隔的路径或 glob（相对仓库根），全局约束写 `project-wide`。它是别的 Agent 按路径找到这篇笔记的主要入口，写宽了没用、写错了会失效，改文件名或移目录时一并更新。`rejected` 也要写：填该方案若被重新提出会落在哪些路径，仓库级选型写 `project-wide`，不要为凑字段编造不存在的路径。
- `Superseded-By`：只在 superseded 时出现，值是同目录下的文件名。

四个二级标题 `Context`、`Decision`、`Alternatives`、`Consequences` 固定，顺序固定，不加别的二级标题。

各状态的含义：

- **proposed**：方案已形成，尚未定案或生效；已授权但尚未实施的目标也使用此状态。只有所需取舍未获授权、存在未解决的分歧或必须由用户决定时才询问，待实施不等于待审批。
- **accepted**：在笔记声明范围内已经实际生效的决策。用户已明确拍板、授权相关技术选择或委托选型时继续实施；生效时直接写 accepted，不必补走审批。一个任务内已完成的选择无需为形式先创建 proposed。
- **rejected**：明确讨论过并否决，且未来仍有参考价值。`Decision` 写被否决的方案，`Alternatives` 写最后采用了什么（通常是维持现状），`Consequences` 写不做的代价。
- **superseded**：曾经有效，已被新决策完全取代。

## 5. Writing Rules

**accepted 用现在时陈述事实**：写「Worker 通过 Message Bus 通信」，不写「将会」「计划」「应该」。读者是半年后只看当前代码的人，笔记跟着代码走。

**不写过程叙事**：「经讨论」「本次修改了」「后续 PR 将」「用户要求」都不要出现，这些是会话残留。

**Alternatives 只写真正考虑过的方案**，不要为凑模板编造。每项写清它为什么在当前约束下合理、为什么没有采用；「不做 / 复用现有方案」只在确实评估过时才写。确实没有任何备选时才可以写：

```markdown
## Alternatives

None — 遵循 [某篇已有约束笔记](./2026-08-01-accepted-example.md)。
```

`None` 必须链接到一篇已有笔记，防止它成为偷懒的默认选项。

**Consequences 必须同时有 Positive 和 Negative**，写成 `- Positive: ...` / `- Negative: ...`。只记真实、具体的内容；Negative 尽量具体到成本、上限或重新评估的条件，识别不出具体代价就重新检查约束和备选，不要编一个来填模板。

篇幅通常 20–60 行，超过 100 行多半是把过程写进去了。

## 6. Back-Pointers in Code

只在「读代码的人会觉得别扭、想简化，但其实是有意为之」的入口处，用项目语言的注释语法加一行：

```ts
// Decision: 2026-09-21-accepted-worker-runtime-boundary.md — Worker 不直接依赖 Main Process
```

一处入口一行就够，不要到处撒。

## 7. Wrap-Up Checklist

1. 这次改动有没有改变某篇 accepted 笔记里的事实（名称、路径、行为）？按第 3 节判断：非核心事实变化就更新原笔记，核心结论变化就新建并取代。
2. 新笔记的 `Status`、`Applies-To`、链接是否正确，`Applies-To` 是否覆盖了实际生效范围？本次创建的 `proposed` 生效后改 accepted，被否决改 rejected；已授权但未完成或用户明确暂缓则保持，说明剩余工作，不重复审批。仍需用户决定的取舍才询问。状态变化按第 4 节重命名并修引用。
3. 笔记和对应代码保持在同一组待交付变更中，执行提交时一起提交；此要求本身不授权 git commit。只改代码不改笔记，是笔记腐烂最常见的方式。
4. 本次改动涉及笔记、`Decision:` 指针或笔记关联的文件路径时，运行项目已接入的结构校验——先查项目协作说明与工具配置，若采用 `npm run verify-decisions`，在项目根目录运行并读取输出。校验只管结构与引用，通过不代表设计理由正确，也不替代第 1 节的检索；失败时修正实际问题，不要为通过校验填充内容。未接入校验器时人工检查并如实说明；除非任务包含接入工具，不要擅自新增 npm 脚本、依赖或构建步骤。
5. 最终回复里用一句话说明新建或更新了哪些笔记，没涉及就不用提。
