# Git Work

让本任务的变化、实际交付内容和验证证据对应起来。读取目标项目的协作说明、提交约定和相关既有决策；已安装 decision-notes 时可按需使用，不要求安装其他技能或工具。

## 工作区与授权

确认仓库、工作目录、分支或 detached HEAD、HEAD SHA、已有工作区和暂存区差异、未跟踪文件，以及正在进行的 merge / rebase 等操作。区分本任务内容和用户、同事、其他 agent 的修改；dirty 工作区本身不要求停止实施。

完成实现不自动触发 commit。提交、推送、合并、发布 tag 和历史重写分别遵循用户或项目已经明确的授权范围；已有授权持续有效，不重复确认。没有某项授权时先完成其余已授权工作并交付可审查结果。

保留外来修改及其暂存状态，不为获得干净目录自动 stash、清空 index、reset 或删除文件。需要提交但 index 混有外来内容时，选择能保留原状态的独立构造方式；不能可靠区分时只暂停受影响的提交。恢复和冲突处理不能覆盖任务开始后的他人工作。

## 构造提交

一个提交表达一个完整逻辑变化，相关实现、测试和必要文档一起交付；无关重构或全局格式化另行处理。按目标仓库规定选择消息格式、身份、签名和 trailer，不默认添加 AI 署名或改写 Git 配置。

暂存前检查修改归属，提交前检查完整实际待提交差异，覆盖新增、删除和重命名。指定路径不能证明其中每一处改动都属于本任务；普通 commit 会包含整个 index，不能只审查刚刚暂存的路径。使用路径参数或其他提交方式时，核对该方式真正生成的候选内容。

共享 checkout 只由一个约定的负责人执行暂存、提交、切分支和集成。最终差异检查、验证和提交期间，协调暂停其他写入；Git 的 index 锁不能防止测试期间文件被改动。需要并行隔离或集成时读取 [parallel-and-integration.md](references/parallel-and-integration.md)。

## 验证与交付

按变化影响执行相关检查和项目要求的检查，不要求每个 commit 跑全量测试。检查通常针对工作目录，提交通常取自 index；部分暂存、外来修改或生成文件可能使两者不同，先核对实际候选内容与受检内容是否一致。

记录足以识别验证对象的状态：已提交内容用 commit SHA，必要时附 tree；未提交内容用 HEAD、可识别的差异或快照及相关未跟踪文件。仅写 HEAD 和 dirty 标记不能证明是哪份内容通过。关键命令、运行目录、结果和未验证范围按任务规模记录在已有计划、交接或 PR 中，不为小改动新建日志体系。

验证后再 commit，内容和验证条件未变时可把证据关联到新 SHA；仅提交消息等元数据变化也可在该条件下复用证据。代码、配置、依赖、运行条件或集成组合变化后，更新受影响的检查与结论。不能把旧分支的“通过”直接归给新版本。

交付说明变化、实际检查及其对象、未解决限制和当前 Git 状态；区分本地完成、已提交、已推送和已集成。清理 worktree 前核对未提交文件、未跟踪及需要保留的忽略文件，并确认提交有持久引用或可恢复归档；clean 不证明成果已经保留，detached HEAD 的成果尤其需要确认。

仅在用户询问 AgentGit / Git AI 或任务确需评估这些工具时读取 [tools.md](references/tools.md)。普通 Git 操作不加载工具调研，也不自动安装依赖。
