# Git 保护与验证底线

按当前动作读取对应章节。本文随入口技能分发，独立安装时仍适用，不要求安装 git-work 或为普通小任务加载完整 Git 工作流。

## 工作区保护

首次写入前确认仓库与工作目录、分支或 detached HEAD、已有 HEAD、工作区差异、完整暂存差异及未跟踪文件；无 Git 时检查现有文件与写入范围。区分用户、同事、其他 agent 和本任务变化，重叠且意图不明时只暂停该范围，其余独立调查和已授权工作继续。dirty 工作区本身不要求停止。

保留已有修改及其暂存状态，不为获得干净目录自动 stash、清空 index、reset 或删除文件。恢复和冲突处理也不能覆盖任务开始后的外来工作；需要调整已有状态时沿用对应授权，无法可靠区分时只暂停受影响的操作。

## 提交与授权

实施、修复、规划、评审或交接完成本身不触发 commit。提交、推送、合并、发布 tag 和历史重写分别遵循用户或项目已明确的授权；已有授权持续有效，不重复确认。缺少某项授权时先交付其余已授权、可审查的结果。

已有提交授权时，暂存前检查归属，提交前核对完整实际待提交差异，覆盖新增、删除、重命名和原有暂存内容。指定路径不证明同一文件内每处改动都属于本任务；普通 commit 包含整个 index，不能只审查刚暂存的路径。其他提交方式也要核对真正生成的候选内容。

提交只包含归属明确的本任务变化，保留外来暂存内容及原状态；必要时使用能保留原状态的独立构造方式，不能可靠隔离时只暂停受影响的提交。相关实现、测试和必要文档按逻辑变化一起交付，消息、身份、签名和 trailer 沿用项目约定，不默认添加 AI 署名或改写 Git 配置。

## 验证对象

验证结论只对应实际检查的内容。检查通常针对工作目录，提交通常取自 index；部分暂存、外来修改或生成文件可能使两者不同，不能把另一份内容的结果归给候选提交。

按任务规模记录关键命令、运行目录、结果和未验证范围，复用已有计划、交接或 PR，不为小改动建立日志体系。已提交内容用 commit SHA，必要时附 tree；未提交内容用 HEAD、可识别的差异或快照及相关未跟踪文件，无 Git 时用可识别文件或快照。仅 HEAD 与 dirty 标记不足以确定受检内容。

已有提交授权时，先完成相应验证再 commit。验证后内容和验证条件未变时可把证据关联到新 SHA，纯提交消息等元数据变化也可复用；代码、配置、依赖、运行条件或集成组合变化后更新受影响检查与结论。按变化影响执行项目要求的检查，不机械要求每个 commit 全量测试；没有新变化或新证据时不重复同一套验证。

## 并行与集成

共享 checkout 由一个约定的 Git 操作负责人管理分支切换、暂存、提交和集成，其他参与者按分工编辑，不自行执行这些 Git 操作。最终差异检查、评审、验证和提交期间，协调暂停影响其对象的其他写入，再固定 SHA 或未提交快照并核对状态；Git 的 index 锁不能防止测试期间文件被改动。

需要不同基线、分别提交或存在写入冲突的独立任务按项目约定使用独立 worktree，确认任务实际需要的起点，不为普通小改动强制创建。worktree 的文件、HEAD 和 index 独立，但共享引用与配置仍需协调；不能擅自提交或 stash 用户修改来制造基线。

集成时固定实际源版本、目标版本及候选结果，在候选组合上完成所需检查后才报告集成通过。各任务分别通过、分支名或 `approved` 状态不能替代版本与组合证据；源、目标或冲突解决内容变化后更新受影响检查。交付区分本地实现、已提交、已推送和已集成。

清理 worktree 或任务分支前核对未提交、未跟踪及需要保留的忽略文件，确认成果已集成或有持久引用、可恢复归档；detached HEAD 的提交尤其要先保留。工作区 clean 不证明成果已保留、推送或集成。
