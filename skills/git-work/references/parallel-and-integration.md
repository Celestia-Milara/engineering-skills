# 并行工作区、集成与恢复

本参考补充任务准备、候选集成及恢复动作；工作区保护、Git 操作者、稳定窗口和验证归属遵循 [Git 底线](git-safety.md)。

## 选择工作方式

按 [Git 底线的并行与集成章节](git-safety.md#并行与集成) 选择共享 checkout 或独立 worktree。隔离单位是任务，只读研究、审查或轻量文件分工不要求每个 agent 建一个 worktree；不能通过强行允许同一分支在多个 worktree 中检出来规避隔离。[Git worktree 文档](https://git-scm.com/docs/git-worktree)

## 准备任务与基线

复用已有计划或任务记录，按需要明确负责人、工作目录、允许修改范围、基线版本、前置依赖、共享接口和集成目标。重叠修改先确定由谁交付或怎样集成；未知负责人影响写入时澄清该范围，独立只读调查可继续。

按底线确认正确起点。当前 checkout 的未提交修改不会自动复制到新 worktree；任务依赖 dirty 内容时，明确要带入的内容、来源及可恢复方式，或先交付依赖再开始。不能在缺少依赖的工作区验证后宣称任务已完成。

共享 checkout 的稳定窗口结束后说明新的基线。另一个 worker 提前暂存的内容不会因使用不同分支名称而获得独立 index。[Git commit 文档](https://git-scm.com/docs/git-commit)

## 集成与证据

worker 交付实际版本、改动范围、验证命令与对应内容、未解决限制；分支名用于定位，SHA 用于确定版本。协调者按依赖顺序选择项目要求的 merge、rebase 或 cherry-pick，不由技能默认改变历史策略。

自动集成或跨任务组合至少固定并核对三个对象：

- **source**：实际待集成的源 commit。
- **target**：构造候选结果时的目标 commit。
- **candidate**：两者集成后的实际内容或 commit。

按 [Git 底线](git-safety.md#并行与集成) 在 candidate 上验证组合；源、目标或冲突解决内容变化时重新构造候选结果。同一 tree 也按验证条件判断能否复用证据。重试或提交前重新核对引用，避免把检查过的版本换成刚移动的分支。

用于保存状态或日志的工具内部 commit，同样遵循 [Git 底线的授权与归属规则](git-safety.md#提交与授权)。

## 冲突与恢复

先确认冲突属于哪个 merge / rebase / cherry-pick、双方意图及目标行为，保留各自必要修改，再按内容解决并执行受影响检查。不能默认整批选择 ours / theirs，也不能把冲突标记消失当作行为正确。

已有授权涵盖合理冲突处理时继续完成，不为每个文件重复询问。无法从需求和代码判断的重要冲突需要澄清；其他独立工作可继续。是否 continue、abort 或改用另一集成方式取决于任务意图和当前状态，没有“永不 abort”的要求。

恢复状态遵循 [Git 底线的工作区保护章节](git-safety.md#工作区保护)。共享已发布历史通常用追加修复或 revert，重写需有对应授权与项目约定。revert 代码不能自动撤销部署、迁移或外部系统副作用，恢复范围必须据实说明。

授权重写远端历史时，`--force-with-lease` 仍需核对目标引用及已审阅的远端预期 SHA；只依赖本地 remote-tracking 引用会受到后台 fetch 的影响。使用明确的预期版本，并在远端变化后重新判断，不以失败为由改成无条件 force。[Git push 文档](https://git-scm.com/docs/git-push)

删除 worktree 或任务分支前，按 [Git 底线](git-safety.md#并行与集成) 核对交付与可恢复状态；忽略文件中仍需保留的成果另行保存。
