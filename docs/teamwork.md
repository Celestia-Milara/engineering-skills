# 3–4 人小团队：只补必要的交接信息

个人模式的技能保持不变；多人协作增加任务归属、共享契约和集成证据即可，不需要额外的 scrum、审批或工单编排技能。

## 一个任务来源

已有 GitHub、GitLab 或其他工单工具就继续使用；没有时用仓库内的一份计划文件。让团队能读取它，别把协作状态留在某个人的临时目录。

不必本地和远端各维护一套状态。Agent 可以先准备本地草稿；是否发布到共享工具遵循用户指令。

多人切片最少记录：

| 字段 | 用途 |
| --- | --- |
| 负责人 | 谁推进、谁提供交接；不能让 Agent 猜人名 |
| 交付行为与验收 | 让接手者能独立判断是否完成 |
| 依赖 | 哪些任务或接口必须先稳定 |
| 状态与交接链接 | 当前进展、分支 / PR / 文件入口 |

个人小改动不需要这张表。普通团队任务通常只需要一段说明和几个验收项。

## 按任务选择工作区模式

| 模式 | 必要边界 |
| --- | --- |
| 单 agent | 修改前核对分支、基线及工作区和暂存区；保留用户原有修改。小任务沿用现有 checkout 即可。 |
| 共享 checkout | 明确文件写入范围，并约定一个 Git 操作负责人协调分支切换、暂存、提交和集成；其他参与者不自行执行这些 Git 操作。 |
| 独立 worktree | 需要独立并行写入、重叠修改或独立验证时按需采用；记录基线和成果 ref/SHA，由集成负责人组合成果。 |

独立 worktree 能隔离工作目录，不同分支仍可能产生接口、行为和迁移顺序上的冲突。分支能合并不代表组合行为正确。上述工作区和成果信息放在同一份任务来源中，不另建一套协作数据库。

基础 Git 边界由各入口携带 [Git 底线](../skills/git-work/references/git-safety.md) 的一致副本，校验器检测漂移；需要具体操作且已安装时可使用 `git-work`。副本保留独立安装能力，维护方式见 [maintenance.md](maintenance.md)。

## 一个共享契约来源

TS 前端和 Python 后端共同开发时，先找到已有 API/schema 或契约文件。明确双方都依赖的字段、空值、错误响应和兼容顺序，再划分任务。无需为了这套 skills 专门引入 schema 工具；已有工具继续用。

领域词汇描述业务含义，schema 描述接口事实，decision-notes 描述非显然原因，计划描述这次怎样交付。通过链接关联，避免四份文件都复制接口定义。

需求级验收选择现有 requirements 或工单作为单一维护来源，计划引用它并补切片级验证。用户调整范围时按已有写入授权同步该来源及受影响切片；暂未同步则标明差异，仅聊天输入不要求另建文档。已授权但未生效的迁移目标保持 proposed，当前 accepted 约束只覆盖已生效范围。

改动共享契约时，指出受影响的调用方与任务。能兼容就分步迁移；不能兼容就明确集成顺序和共同验证点，不能仅靠本地 mock 通过就让依赖方开始集成。

## 一个明确的集成结论

各人使用项目既有分支 / PR 方式。存在重叠改动时先比较意图与依赖，不覆盖同事工作。多分支同时修改同一决策状态时，在集成版本中核对现行 accepted 结论、取代链以及所有改名引用。

PR 或交付说明最少包含：解决的问题、验收结果、运行过的检查、共享契约或迁移影响、未完成事项。决策笔记与对应代码在同次变更交付，记录实际源成果和目标集成版本，并在组合版本上运行受影响的检查。

最终评审和集成验证时暂停影响目标范围的写入，固定实际 SHA 或未提交快照；暂存内容与工作目录也要对应验证范围。验证后若相关内容又变化，更新受影响的验证证据；内容未变且检查已充分时不无条件重跑。成果 ref/SHA 证明来源，不能代替验收通过。

“实现完成”“评审完成”“集成验证通过”是不同事实，可以用自然语言说明，不强制新增状态机。仅请求评审不意味着允许修复、提交或合并。

提交、推送和合并遵循用户已有授权，不因切片或检查完成而默认自动执行。已有提交授权时，Git 操作负责人核对拟提交的完整 diff 和暂存归属，只纳入本次工作；不会为了得到干净目录清理用户、同事或其他 agent 的修改。

## 可以直接使用的任务描述

```text
用 plan-work 将这个 TS 前端 + Python API 的功能拆成可验证切片。
我们有 3 人，先给出职责建议，不替我们指定人名。
复用现有 API 契约，标出哪些工作能并行、哪些必须先集成。
把计划保存在仓库现有的团队计划目录。
```

```text
用 review-work 评审这个 PR，特别检查与尚未合并的 API 变更的依赖。
区分本 PR 的缺陷和必须等上游集成才能验证的内容，先不要修改代码。
```
