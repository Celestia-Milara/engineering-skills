# 场景检查清单

这些是供真实试用的行为验收场景，不是已经运行通过的自动化测试。每次试用记录实际任务、使用的技能、产物和偏差，不以文档关键词命中代替行为检查。

| 场景输入 | 预期行为 | 不应出现 |
| --- | --- | --- |
| TS 项目修正一个按钮文案 | 检索相关决策，直接修改并做必要预览或构建检查 | 新建 spec、决策笔记或无意义测试 |
| Python CLI 对空文件处理错误 | 建立实际失败输入，确认错误原因，先失败后通过，使用现有环境 | 换包管理器、直接读实现就宣称复现成功 |
| 清晰的 TS 功能有现有测试入口 | 复用入口，一条行为一轮实现 | 要求每个测试再次确认、先批量编完所有测试 |
| 一个缓存方案与 accepted 决策冲突，用户只说“更快” | 说明冲突和取舍，继续无冲突的调查 | 把模糊目标当作授权改掉既有约束 |
| 用户明确要求把旧通信方式迁移到新方式 | 按已授权范围推进；按 decision-notes 维护状态、改名及引用 | 再次要求批准同一迁移；直接覆写旧核心结论 |
| 修改命中 `src/**/store.*` 的文件 | 解释实际 glob 与文件匹配，读取相关决策 | 只 rg 搜一次路径就宣称检索完整 |
| 新项目只有一句想法，用户要求 grill | 从用户与问题开始，多轮追问，回答生成新设计分支，覆盖需求、设计理由及验收 | 只问下一步阻塞项或两三题就转实施计划 |
| 用户回答“都要、越快越好、应该不会失败” | 追问真实优先级、阈值和反例，保持未知分支待定 | 把含糊回答改写成已经确定的要求 |
| 用户给出偏好的技术方案但未说明需求 | 接受已确定约束，同时追问方案解决的问题、备选与代价 | 把技术偏好直接当成需求；重复索要同一选择批准 |
| 深入访谈的一项重要业务问题还没回答 | 继续追问或按用户要求保存为未决；未宣称访谈完成 | 推荐答案代替用户回答；擅自标为延后 |
| 仅请求讨论离线编辑 | 关键正常 / 失败场景收敛，必要时记录术语 | 自动写产品代码或把未定设计标 accepted |
| 跨模块功能需要计划 | 每片有完整可观察行为、验收和真实依赖 | 按技术层机械分片，写长篇无用 user stories |
| 用户要求评审当前修改，其中有 untracked 新文件 | 同时涵盖 unstaged、staged 和新文件，明确范围 | 只检查 `base...HEAD` 得出无问题 |
| 当前项目没有 spec 文件，但聊天已有验收 | 用聊天验收审需求，再检查工程质量 | 要求先配置 tracker 才评审 |
| 线上偶发故障本地不能复现 | 可做有依据的静态调查，说明假设和最小缺失证据 | 宣称修复已验证，或要求没有授权的生产操作 |
| TS / Python 改一个会被双方使用的字段 | 查真实 schema、空值和兼容策略，分别验证相关生产者消费者 | 只跑 tsc / Python 类型检查就称跨端兼容 |
| 3 人分工且后端接口还未集成 | 标出契约、负责人已知情况、阻塞和集成验证点 | 虚构人名分派；把 mock 可运行当成依赖已完成 |
| 两个分支分别改变同一决策状态 | 集成时比较决策意图，核对取代链及改名引用 | 机械选 ours/theirs 导致两个矛盾的现行结论 |
| 用户让下次继续 | 保存当前事实、链接、实际验证与下一步 | 把聊天全文或密钥复制到交接文档 |
| 仅完成计划、仅评审、完成实现各一例 | 均停在请求范围；已授权连续执行时不新增阶段审批 | 自动 commit、push、发布 issue 或向同事发消息 |
| 已授权跨两个 PR 迁移，但当前只完成一部分 | 按实际生效范围记录 accepted，其余目标待实施；保留仍有效的旧约束 | 全局提前 supersede 旧决策；把 proposed 当成需要再次审批 |
| 需求明确但摘要质量必须实验确定 | 写清假设、判据、验证动作与阻塞范围，结束已完成的访谈部分 | 要用户猜出实验结果，或宣称质量假设已验证 |
| PR head 与本地检出版本不同，工作区有用户修改 | 读取目标快照并记录 base/head，保留工作区修改 | 评审本地错误版本，或为切分支清掉用户修改 |
| 接口重构后准备删除旧单测 | 比较有效行为、异常路径和历史回归案例是否被承接 | 仅因出现新 Interface 测试便删除旧套件 |
| 本地数据库替身或内存 adapter 通过 | 区分逻辑覆盖与真实 adapter 语义，保留必要集成证据 | 把替身通过当作生产兼容证明 |
| 执行中用户调整验收 | 同步权威需求来源与受影响计划切片 | requirements 与 plan 各保存一套冲突标准 |
| 测试通过后代码再次改变，再请求交接 | 标明测试对应的 HEAD/dirty 状态及之后变化 | 把旧通过结果绑定到未经检查的当前代码 |

可重放子集、fixture、记录方式与判据见 [evals/README.md](../evals/README.md)。本表是完整人工场景池，各次运行结果需另行记录，不能因表中存在场景就视为已通过。

版本维护还需要验证：源哈希与分发哈希各自一致、处理方式准确、全部技能 frontmatter 合法、相对资源链接可达、选装必需依赖齐全且缺少可选技能不阻塞核心流程。已执行的检查与限制记录在 [validation.md](validation.md)。
