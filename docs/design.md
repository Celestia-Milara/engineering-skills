# 设计取舍与来源映射

## 目标

保留 decision-notes 的轻量机制，补齐从想法到交付的工作方法；主要服务 TS / Python 项目，也能支持 3–4 人通过共享任务和 PR 协作。技能按具体任务触发，不接管整个开发过程。

以下判断基于本机两个来源仓库的快照，版本记录在 [sources.json](../sources.json)，不是对上游未来版本的承诺。

## decision-notes 的适配

来源为 `decision-notes-skill/template/.agents/skills/decision-notes/SKILL.md`。本版标记为 adapted：明确区分继续实施的授权与描述现状的生命周期，允许在同一任务内复用未变化的检索结果，并明确同次交付不自动触发提交。

保留扁平目录、文件名状态、四种生命周期、Applies-To 检索、反向指针、按需记录、同次变更交付、可选且只检查结构的校验器。具体规则只有本版 decision-notes 一处定义，其他技能引用它。

用户已授权即可实施，无需重复审批；目标尚未生效时保持 proposed，实际生效后才写 accepted 或取代旧笔记。分阶段迁移按生效范围描述，新旧约束不能互相冲突。本地代码事实与生产部署事实分别需要对应证据。计划保存实施状态，决策笔记保存原因与约束。

没有修改源仓库，所以不需要同步它的根目录与 template 副本。本库保留自己的分发快照，未来更新需明确比较版本。

本版 decision-notes、tdd、codebase-design 与来源安装会重名，项目中选择一个版本；其他改编入口换名，避免混淆维护来源。

clarify-work 的深入访谈保留 grill 的核心作用：Agent 主动追问，回答产生新分支，持续揭示含糊需求、隐含假设、冲突与未解释的选择。不能以“已经可以开始写代码”结束项目初期访谈。局部任务使用另一种轻量深度，不能据此削弱用户明确要求的深入访谈。

与上游的适配集中在已有授权、文档位置和执行能力：不重复批准已确定事项；环境事实由当前 Agent 调查，不强制派子 Agent；长期设计理由按本版 decision-notes 的状态与格式维护。深入访谈仍需要用户真实回答，不能用推荐选项或沉默代替答案。只能通过实验回答的假设，在需求、判断标准、验证动作与阻塞范围明确后可保持待验证，不把实验性未知变成无休止的访谈。

## 设计方法的适用边界

`codebase-design` 用深模块、调用方认知成本和变更集中度比较方案。术语映射到项目已有语言，不要求替换 API、service 等用词；纯计算或接口较少本身不证明应当合并模块。仅在接口设计或结构问题上读取相应参考。

项目已有约束和本次用户范围优先。旧测试只有在有效行为、异常路径和历史回归案例被新验证承接后才考虑移除；多 agent 不可用或不值得时在当前会话比较方案。这些规则已写入技能目录内，独立安装不依赖读取本设计文档。

测试默认验证稳定行为。为确定性、故障注入或昂贵依赖隔离可使用替身，对依赖的所有权不单独决定能否 mock；替身不能证明生产 adapter 的序列化、事务、网络故障等语义，保留相应契约或集成验证。

对于偏好更少技能的项目，可以暂不安装 codebase-design，实施技能也不依赖它才能运行。TDD 的上游参考示例使用 TypeScript，但入口和方法不绑定语言；对外部交互契约的必要断言，以实际行为需求为准。

## Git 规则的接入

新增 [git-work](../skills/git-work/SKILL.md) 是本库原创，来源清单使用 `original` 与分发哈希，不伪造上游对应文件。它可独立安装，也不成为其他技能的必需依赖。现有执行入口保留工作区、暂存归属和共享目录单一 Git 操作者的必要边界；复杂提交、隔离、集成和恢复按需读取 git-work。普通实现仍不默认提交；项目可在协作说明中明确允许本地提交，push、合并和共享历史重写各自沿用已有授权。

隔离单位是独立实现任务，不要求每个 agent 都建 worktree。共享目录按修改范围分工，由一个负责人操作 Git，在最终验证与提交窗口暂停其他写入。独立任务交付固定源版本，集成者核对目标和候选组合，验证结论绑定实际内容；任务状态或分支名不能代替版本。纯提交消息变化且内容与验证条件未变时可复用证据，不机械地要求每个 commit 全量测试。

任务负责人、修改范围、基线、交付版本和检查复用已有计划、交接或 PR；decision-notes 仍只保存长期理由。借鉴编排型 AgentGit 的任务与验证思路，但不增加 `.agentgit` 任务数据库，也不采用未经版本绑定的 `approved` 合并闸门。会话工具与 Git AI 仅在确有交接或来源归因需求时评估。调研日期及所读实现限制保留在 [工具参考](../skills/git-work/references/tools.md)，不成为每次提交的必读资料。

新项目使用根目录 [AGENTS.example.md](../AGENTS.example.md) 填写真实事实并提取为项目 AGENTS.md；已有项目使用 [AGENTS.snippet.md](../templates/AGENTS.snippet.md) 合并。完整模板只维护一份，底线与按需路由在两种入口保持一致，不将本库维护命令带入业务项目。

## 暂不纳入的上游流程

- **ask-matt / setup-matt-pocock-skills**：面向上游整套工具路由与 tracker 配置，本库用一张选择表和 AGENTS 片段即可。
- **triage / wayfinder**：工单状态与大型探索编排超出当前轻量需求。需要时可单独评估，不为了 3–4 人团队先引入。
- **prototype**：概念有用，但原版包含特定 HTML/UI 产物和保存分支流程。实际需要验证交互或状态模型时再接入，避免默认扩大到原型归档。
- **research**：原版默认后台 agent。当前代码与官方资料调查由相应任务按需完成，暂不加独立研究编排。
- **improve-codebase-architecture**：全库扫描、报告和访谈不是每次开发的前置条件。先用 codebase-design 解决明确的局部问题。
- **resolving-merge-conflicts**：原版包括完成 merge/rebase、永不 abort 等较强操作约束；本版 git-work 按实际意图、双方行为和可恢复状态处理冲突，不复用整套动作。
- **wizard / setup-pre-commit 等工具配置技能**：按项目实际需要单独加入，不默认所有 TS / Python 项目需要相同工具链。

## 产物与协作

访谈形成的需求文档回答“谁遇到什么问题、要什么行为、还不知道什么”，计划回答“本次怎样切片交付”，decision-notes 回答“长期为什么这样做”，词汇表回答“这个业务词指什么”，交接回答“现在从哪里继续”。已有产物优先复用，关键决策用链接连接，不复制第二份正文。

需求级验收选定一处权威来源，计划引用它并只增加切片级验证；只有聊天输入时计划可成为简明要求的维护来源。按已有写入授权同步需求变更及受影响切片，暂未同步则标明差异。PR 评审绑定实际 base/head 与读取的代码，发现归因到本次变更；交接中的验证结果绑定检查时的代码状态，不用分支名代替版本。

3–4 人协作只在需要拆分时给切片增加负责人、依赖、契约入口和集成状态。没有现成协作平台时，版本控制中的计划已足够；已有平台时它就是任务来源。技能不自动给同事分任务、发消息或发布工单。

## 后续迭代

先用 [行为评测](../evals/README.md) 的固定场景，在相同初始状态下比较无技能、最小组合与完整组合；重复运行后比较结果、错误动作和成本。独立少量试用不等同于统计上已证实收益。再跑真实 TS 功能、Python 修复和多人跨端变更，按具体偏差改入口。

维护检查集中在一个脚本中，校验分发哈希、依赖与链接。暂不改变决策文件名协议或引入新索引；先观察笔记增长后的检索成本及多人改名冲突，避免让现有项目和校验器承担未验证的迁移成本。

本版静态检查不能证明模型真实调用时一定表现正确，试用标准见 [scenarios.md](scenarios.md)。
